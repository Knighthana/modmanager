## 一、仍待裁定（阻塞写 SPEC）

### P1 — .kmmignore 原语工单化：备份能走通，恢复是障碍

**已裁决**：Planner 不执行文件操作。`.kmmignore` 的备份/恢复由 Planner 生成工单条目，原语执行。

#### 备份方向 ✅ 能走通

`run_differential_backup(backup_dir, files_to_backup, *, content_root, ...)`：
- `files_to_backup` 是绝对路径的列表
- 内部推导：`rel = src.removeprefix(content_root).lstrip("/")`, `dest = backup_dir / rel`
- 当前 `_copy_kmmignore_to_backup` 的逻辑是向上遍历目录树发现 `.kmmignore` 文件，Planner 完全可以预先遍历，将发现的绝对路径追加到 `files_to_backup`
- 即使 `.kmmignore` 在 `content_root` 之外（祖先目录），`rel` 会退化为绝对路径镜像，文件仍能正确复制，备份/恢复的路径推导一致
- **结论：无需改造原语。Planner 将向上遍历发现的 `.kmmignore` 绝对路径加入 `files_to_backup` 即可**

#### 恢复方向 ❌ 不能走通

`restore_entries(entries_by_backup_dir, backupinfos, ...)`：
```python
for entry in entries:
    rel_path = _relative_to_backup_root(target_path, backup_dir)
    node = _find_tree_node(tree, rel_path)
    
    if node is None:
        os.remove(target_path)    # ← 树里没有结点 → 删除目标文件！
```

备份树（`backupinfo.json`）只包含 mod 文件结点。`.kmmignore` 不在 tree 中：
1. `_find_tree_node(tree, rel_path)` → `None`
2. 触发 `os.remove(target_path)` ——**误删除**，而非恢复

这就是障碍：恢复原语依赖 tree 判断恢复/跳过/删除，`.kmmignore` 不属于任何一个 tree 结点。

#### 方案

| 方案 | 备份侧 | 恢复侧 | 侵入度 |
|:---:|--------|--------|:---:|
| **A** | Planner 加入 `files_to_backup` | `restore_entries` 加 `extra_pairs` 参数，其中的条目不检查 tree，无条件执行 `copy2(backup_copy, target)` | 中 |
| **B** | 同上 | Planner 在计划恢复时配对 backup 副本↔原始目标，`_execute_restore_plan` 单独处理，不走 `restore_entries` | 中 |
| **C** | 同上 | 把 `_copy_kmmignore_from_backup` 的 `os.walk` 逻辑移入 `_execute_restore_plan`——执行层而非 Planner 做 I/O | 低（但打破纯I/O分离） |

> 注意：你之前说"文件操作全部交原语办理"→ A 最干净。若选 C，则恢复侧的 Planner 仍在"做 I/O 决策"，与 DataPort 设计的 I/O 边界有张力——但这里是业务文件操作，不在 DataPort 管辖区内，严格来说不冲突。

**← 等你选。**
